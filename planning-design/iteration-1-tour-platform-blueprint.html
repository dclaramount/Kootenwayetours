Design & architecture proposal

A monolithic web platform for a tour-guide business

Reviewed cenotescasatortuga.com for inspiration, then designed an independent site and admin platform — TypeScript end to end, React frontend, one deployable backend, Postgres, and a path to Civo Kubernetes.

01

Reference site: structure, content, and patterns

Everything below is what the reference site actually does today. It's marked Observation throughout — none of it is a recommendation yet.

Information architecture

Primary nav: Inicio, Cenotes (4 named cenotes), Actividades (4 activity types), Restaurantes (4 venues), Paquetes, an external Hotel link, Eventos (Bodas / Grupos), Fotografía, Contacto. The footer repeats most of this and adds Nosotros, Términos de Servicio, and FAQ. Every cenote and every restaurant gets its own URL (campana.php, wisho.php, dorca.php, treszapotes.php …) rather than living as sections of one page.

Homepage, top to bottom

  1. Header with logo and social icons
  2. Hero slider — three rotating taglines ("Disfrute de las maravillas de la naturaleza", "Vuela sobre la selva maya", "Explora la herencia maya"), each with Reserve / Contact buttons
  3. A booking widget (package, adults, children, date) — visibly stubbed, showing "Próximamente" (coming soon)
  4. A short "welcome to the cenote paradise" section
  5. Six activity cards (Tirolesa, Kayak, ATV's, Tour, Buceo, Senderismo), each a "see more" link with almost no supporting detail
  6. An about block with two feature icons
  7. Three package cards — Básico / Silver / Golden
  8. A 7-image gallery grid opening in a lightbox
  9. A newsletter sign-up
  10. Footer: company info, social links, contact details, an Instagram feed repeating the same activity photos

The paquetes.php listing page confirms this is the full extent of the detail: no itinerary, no inclusion/exclusion list, no difficulty or fitness notes, no photos beyond one hero image per card, and no comparison view. "Reservar" is the only call to action and its destination is ambiguous — it isn't clear whether it opens a form, a cart, or just scrolls to contact details.

Calls to action, contact, and the booking flow

CTAs repeat constantly but say few distinct things: Reservar, Contacto, Más Información, Contactar, plus a floating WhatsApp button. Contact details are genuinely thorough — phone, two email addresses, a full street address (given in two slightly different formats on different pages), hours, and six social platforms. The booking widget is present on multiple pages but explicitly marked "coming soon," so today the site's real conversion path is WhatsApp or email, not a self-serve checkout.

Blog and gallery

A "Recent Posts" sidebar lists two entries whose titles ("Where Vision Meets Concrete Reality", "Raising the Bar in Construction") read as leftover template content, not tour-business copy — a sign the CMS or theme was never fully localized to the business. The gallery is a single flat grid of 7 photos plus a Grid of Instagram images; there's no per-cenote or per-activity photo album, and no captions or attribution.

Strengths

  • Contact information is redundant and easy to find (phone, email ×2, address, hours, WhatsApp, six social links)
  • Clear activity taxonomy (cenotes vs. activities vs. restaurants vs. events) that maps to how the business actually operates
  • Nature photography is used consistently as the visual anchor of the brand

Weaknesses

  • Booking is advertised but not implemented ("Próximamente"), which sets an expectation the site can't meet
  • Pricing/package data is inconsistent in structure (package names differ between the homepage and the packages page — "Silver" vs. "Silver 1 / Silver 2") and carries almost no itinerary detail
  • Blog contains unrelated placeholder content, suggesting no real content workflow behind it
  • One flat gallery with no organization by tour, cenote, or date
  • Duplicate/contradictory address formatting across pages points to no single source of truth for business info
  • Multiple page-template styles (.php pages vs. static .html pages like tour-details.html) suggest an inconsistent, possibly patched-together build

Typography

A warm serif display face for headings (evokes carved stone/signage without being a cliché travel-brand script), paired with a clean grotesque for body text and UI, and a monospace for data-like details (durations, prices, dates) so numbers line up.

Spacing & responsive behavior

Generous section spacing on desktop collapses to a single column with larger touch targets on mobile; the sticky contact bar (call/WhatsApp/email) stays reachable at all breakpoints, mirroring the one part of the reference site's mobile behavior worth keeping.

05

Technical architecture

Recommendation

One Next.js application (TypeScript, App Router) provides both the public/admin frontend and the JSON API, so "monolith" means one codebase, one build, one container, one deployment — not a split frontend/backend that happens to ship together.

  • Public pages (/, /tours/*, /journal/*, /gallery, /contact) render as React Server Components for fast loads and clean SEO — no client-side data fetch needed for first paint.
  • The admin UI (/admin/*) is an authenticated client-heavy area using the same App Router, calling Route Handlers under /api/* for mutations.
  • Route Handlers double as the "backend API" the brief asks for — they're ordinary HTTP endpoints, testable and reusable independent of the React layer.

08

Admin content workflow

Recommendation
  • Login — rate-limited, generic failure messages, account lockout after repeated failures; no public registration exists anywhere in the app.
  • Dashboard — tours, posts, and media each list with a status badge (Draft / Published / Unpublished) and last-edited info.
  • Editing — slug auto-generated from title, editable with uniqueness validation; rich-text body via Tiptap; every field validated with the same Zod schema client and server side.
  • Publishing — explicit Publish/Unpublish action toggles status and stamps published_at; drafts are never reachable on public routes regardless of a guessed URL.
  • Media library — drag-drop upload with automatic processing (§9), search/filter, alt-text required before an image can be attached to published content, "replace" keeps the same media record so existing tour/post references don't break, "delete" soft-deletes and is caught by the orphan-cleanup job.
  • SEO panel — meta title, meta description, slug, and OG image, shared across tours and posts as one component.
  • Audit log — every create/edit/publish/delete is recorded with actor, timestamp, and a diff, viewable per entity.

09

Image upload, optimization & storage strategy

Recommendation

Everything is sized to fit comfortably inside the 5 GiB uploads volume, with visibility into usage before it becomes a problem.

Pipeline

  1. Accept JPEG/PNG/WebP/HEIC only, capped at 15 MB pre-processing; reject everything else by sniffing actual file bytes, not just the extension or declared MIME type.
  2. Strip EXIF metadata (privacy + size) and re-encode with sharp, which also neutralizes any payload hidden in the original file.
  3. Generate four variants as WebP: thumbnail (320px), medium (800px), large (1600px), and a display "original" capped at 2560px — the true uploaded original is discarded once variants exist.
  4. Store only the processed files, under content-hashed filenames, on the persistent volume; record paths and sizes in media.variants.

Budget

Four WebP variants at quality ~75–80 average roughly 500–700 KB per source image. At that rate, 5 GiB holds on the order of 7,000–9,000 images — far beyond what a single tour operator's catalog, gallery, and blog will realistically need (more likely a few hundred to low thousands over several years). The admin dashboard should still surface current usage and warn at 80% of quota, and the upload endpoint should reject new uploads once the volume is effectively full rather than fail unpredictably mid-write.

Cleanup

A scheduled job (Kubernetes CronJob) finds media rows with no active reference in tour_media, blog_post_media, or gallery_items and past their soft-delete grace period, then removes the files and the row — so deleting a tour or swapping a cover photo doesn't silently leak storage.

10

Local development setup

Recommendation
  • docker-compose.yml runs Postgres locally, matching the production engine/version; the app itself runs via npm run dev against it for fast iteration, or in Docker for a closer prod parity check.
  • Local uploads write to the same relative path the production PVC mounts (e.g. /data/uploads), just backed by a bind-mounted folder instead of a cloud volume — so upload/serve code never branches on environment.
  • .env.example documents every variable (DATABASE_URL, SESSION_SECRET, UPLOAD_DIR, NODE_ENV, mail provider keys).
  • prisma migrate dev plus a TypeScript seed script create a default admin user and a handful of realistic sample tours/posts/images, so a fresh clone looks like a working site immediately, not an empty shell.
  • Quickstart: cp .env.example .env → docker compose up -d postgres → npm install → npm run db:migrate && npm run db:seed → npm run dev.

Docker, GitHub Actions & Civo Kubernetes plan

Recommendation

Docker

Multi-stage Dockerfile: install/build stage, then a slim node:<current LTS>-alpine runtime stage running as a non-root user, containing only production dependencies and the compiled build.

GitHub Actions (build & validate, per the brief's scope)

On every push/PR: checkout → set up Node with dependency caching → npm ci → typecheck → lint → unit tests → next build → docker buildx build. On main, additionally push the image to GHCR tagged with the commit SHA. 12

Cross-cutting concerns

Recommendation

Security

  • Argon2id password hashing; httpOnly/secure/SameSite session cookies; CSRF protection on all state-changing routes
  • Zod validation at every API boundary; rich-text content sanitized before storage and before render to prevent stored XSS
  • Uploads validated by content-sniffing, size-capped, and re-encoded through sharp (which also strips embedded payloads); SVG uploads disallowed
  • Rate limiting on login and the public enquiry form; least-privilege database user; security headers (CSP, HSTS, X-Frame-Options)
  • Dependency scanning in CI; no secrets ever committed; full audit trail per §8

Backups

Nightly pg_dump and a nightly uploads sync (via restic or rclone) both push to Civo Object Storage with a retention window (e.g. 14 daily + 8 weekly); a periodic restore drill is worth scheduling once real content exists.

Migration safety

Prisma Migrate with reviewed, checked-in migration files; migrations run as a pre-deploy step (init container or CI gate) rather than on app boot, so a bad migration blocks the rollout instead of racing multiple pod starts.

Observability

/api/health (process liveness) and /api/ready (DB connectivity) for Kubernetes probes; structured JSON logs via pino to stdout; optional Sentry integration for exception tracking once the app is live.

Accessibility

Semantic HTML, mandatory alt text on every image (enforced in the admin form, not just encouraged), WCAG AA contrast in the palette in §4, full keyboard navigation, visible focus states, labeled form fields with real error text.

SEO

Editable meta title/description/slug/OG image per tour and post; auto-generated sitemap.xml and robots.txt; canonical URLs; JSON-LD structured data (tour → TouristTrip, post → Article, site → LocalBusiness); the redirects table from §7 keeps old links alive when a slug changes.

Performance

Server-rendered/ISR public pages with on-demand revalidation triggered by a publish action, so editors see updates go live immediately without a full rebuild; optimized image variants from §9 double as the performance strategy for photography-heavy pages.

13

Assumptions, risks & open questions

Decision needed

Online booking/payment is treated as optional, per the brief — the initial site uses an enquiry form (name, email, phone, tour, message) plus WhatsApp/phone/email as the conversion path, matching what actually works on the reference site today. Adding real booking later would need: a payment gateway (Stripe Checkout is the simplest way to keep card data out of PCI scope), an availability/capacity model per tour and date, and a cancellation/refund policy captured in the data model.

Decision needed

Language. The reference site is Spanish-only; I've assumed the new site launches in English (the brief and this workspace are in English) but the content model — separate title/description/excerpt fields per entity — is structured so a second locale could be added without a schema rewrite. Confirm target audience/languages before content entry begins.

Decision needed

Transactional email provider for enquiry notifications (e.g. Resend, Postmark, or SMTP through an existing provider) isn't specified — needs a choice before §8's enquiry flow can actually notify anyone.

Decision needed

Domain name and Civo cluster sizing (node count/size, existing or to-be-provisioned) aren't known yet — both are needed to finalize the Ingress/DNS/TLS setup in §11 and to size pod resource requests.

Assumption

The 5 GiB figure applies specifically to uploaded media, per the brief's wording. Postgres data is assumed to need its own, separate volume allocation — worth confirming before cluster storage is provisioned.

Assumption

One admin role is sufficient at launch (no editor/approver distinction). The role column in §7 is there so finer-grained roles can be added later without a migration to add the concept from scratch.

Risk

Single replica, uploads on a PVC. Because uploads live on a ReadWriteOnce volume, only one pod can mount it at a time — this rules out horizontal scaling and means a brief gap during rolling deploys (mitigated with a short readiness-gated rollout, not a true zero-downtime deploy). It's a reasonable starting point at this traffic scale. The clean upgrade path, if traffic or availability needs grow, is moving uploads to Civo Object Storage (S3-compatible) — that removes the single-writer constraint entirely and unblocks multiple replicas without any change to the data model.

Risk

Image processing (sharp) is CPU/memory-bound at upload time; the app pod's resource requests/limits need real-world testing against typical phone/camera photo sizes before they're finalized.

Phased implementation plan

Each phase produces something runnable; nothing here starts until this proposal is approved.

P1

Project scaffolding

Next.js + TypeScript app, Tailwind, Prisma + Postgres wiring, Docker, local docker-compose, CI pipeline (lint/typecheck/test/build), base layout using §4's palette/type, health endpoints.

Milestone npm run dev works locally; CI builds the Docker image on every push.

P2

Data model & admin auth

Prisma schema + first migration, seed script, Auth.js credentials login, protected /admin shell, audit-log scaffolding.

Milestone An admin can log in and see an empty dashboard, deployed to a dev environment.

P3

Content management

Full tour and blog-post CRUD, publish/unpublish, slug handling, SEO panel, rich-text editing.

Milestone Admin can manage tour and blog content end to end.

P4

Media pipeline

Upload endpoint, sharp processing, media library UI, assignment to tours/posts/gallery, usage tracking, orphan-cleanup CronJob.

Milestone Images upload, optimize, and attach to content within the storage budget from §9.

P5

Public website

Home, tour catalog/detail, journal listing/detail, gallery, contact/enquiry form, responsive polish, sitemap/robots.

Milestone Full public site is navigable and entirely content-driven, locally.

P6

Hardening

Security headers, rate limiting, CSRF, sanitization audit, accessibility pass, Lighthouse/performance pass, error tracking.

Milestone A dedicated security review passes clean; Lighthouse scores meet targets.

P7

Kubernetes deployment

Write and apply the §11 manifests, Ingress + TLS, secrets, backup CronJobs, deploy to the Civo cluster, smoke test.

Milestone App running on Civo, reachable over HTTPS, with backups configured and verified.

P8

Optional / future

Online booking + payments, a second language, multi-admin roles, migration to object storage for uploads to unlock multiple replicas.

Milestone Scoped and estimated only once the core platform is live and real usage data exists.
